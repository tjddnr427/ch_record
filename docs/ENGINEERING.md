# 구현 및 리뷰 기준

## 최소 구조
Phase 0은 실행 가능한 작은 PoC로 시작한다. GPU 추론과 오디오 장치가 실제로 동작하는지 확인하기 전에 전체 GUI·작업 큐·배포 구조를 미리 구현하지 않는다.

향후 제품 코드는 UI, 작업 조율, 외부 도구 어댑터의 책임을 구분한다. 데이터와 시간 계산은 가능한 한 일반 Python 함수·작은 데이터 구조로 작성한다. 실제 변경이 생길 때 모듈을 분리하며 빈 디렉터리와 빈 계층을 미리 생성하지 않는다.

## SOLID 적용
- S: UI 표시, 작업 상태 전이, 음성 추론, 장치 캡처, 파일 저장은 각각 변경 이유가 다르므로 분리한다. 한 기능을 불필요하게 여러 클래스로 쪼개지 않는다.
- O: faster-whisper, 캡처 라이브러리, FFmpeg, SQLite 같은 교체 가능한 외부 의존성을 어댑터에 모은다. 새 구현은 필요한 경계에서 교체하며 미래 플러그인 체계를 미리 만들지 않는다.
- L: 대체 구현은 반환값·오류·취소·자원 해제 계약을 지킨다. 지원하지 않는 동작을 성공으로 처리하거나 조용히 생략하지 않는다.
- I: 호출자가 쓰는 기능만 노출한다. 추론·녹음·저장을 한 거대 인터페이스에 묶지 않는다.
- D: 작업 조율 코드가 Qt 위젯이나 특정 장치 라이브러리의 내부 객체에 의존하지 않게 한다. 외부 의존성은 생성자 또는 함수 인자로 전달하고 조립은 진입점에서 한다.

Protocol이나 인터페이스는 외부 의존성 격리, 테스트 대체, 실제 복수 구현 중 하나의 이유가 있을 때만 만든다. 작은 순수 함수에는 클래스를 강제하지 않는다. 상속보다 조합을 우선하며 동일한 계약을 실제로 제공할 때만 상속한다.

## 과잉 설계 방지
- 범용 프레임워크, 플러그인 로더, DI 컨테이너, 범용 이벤트 버스, 모든 엔티티의 Base 클래스는 현재 요구사항 근거 없이 추가하지 않는다.
- 설정은 사용자 선택 또는 실제 환경 차이가 있는 값에 한정한다.
- 한 번 쓰는 코드를 미래 재사용만을 이유로 공통화하지 않는다. 중복 제거는 서로 같은 변경 이유를 갖는지 확인한 뒤 한다.
- 과도한 래퍼, 무의미한 전달 메서드, 사용하지 않는 확장점과 의존성을 제거한다.
- 도메인 코드가 외부 도구의 형식에 묶이지 않도록 필요한 데이터만 작은 구조로 전달한다. 대규모 공통 모델을 미리 정의하지 않는다.

## 변경에 대한 계약
외부 경계에는 입력·출력, 단위(ms/초, sample rate), 오류, 취소, 자원 소유권을 기록한다. 특히 STT와 캡처는 타임라인 기준과 원본 보존 정책을 명시한다. 라이브러리 객체나 예외가 UI까지 무분별하게 새어 나오지 않게 한다.

## 검증과 리뷰
외부 동작과 실패 위험을 검증한다. 구현을 그대로 따라 쓰는 테스트와 단순 getter 테스트는 만들지 않는다. 복구·취소·타임라인·파일 확정 등 중요한 계약을 우선한다.

리뷰에서는 다음을 확인한다.
- 현재 PRD 요구사항으로 설명할 수 있는 변경인가?
- 더 작은 함수나 모듈로 같은 동작을 명확히 제공할 수 있는가?
- 외부 라이브러리 변경이 관련 어댑터 밖으로 불필요하게 번지는가?
- 대체 구현이 오류·취소·자원 해제 계약을 지키는가?
- 추가된 추상화가 실제 변경 또는 검증에 도움이 되는가?
- 실제 GPU·오디오 검증과 mock 결과를 구분했는가?

필요 없는 추상화는 단순화하고, 필수 복구·검증은 비용 절약을 이유로 생략하지 않는다.
